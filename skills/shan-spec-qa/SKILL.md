# Shan Spec QA — 規格品保

spec 文件的品質保證。它站在「spec 產生」與「下一個人接手」之間——誰寫的初稿都行（`shan-to-req`、`shan-to-spec`、外部工具、手寫），**但初稿不是交付物**。

團隊流程下它守兩道交接：**SA → PG**（requirements 與 SD 能不能交出去）與 **PG → 開發**（design／tasks 是否忠於 requirements 與 SD）。用同一支 skill，靠模式區分。

全程繁體中文（台灣用語）輸出。

---

## 為什麼需要這道關

spec 的錯誤會被**完整放大**到實作。而 spec 的問題有兩種，性質完全不同：

**機械性問題**——編號斷裂、交叉引用指向不存在的條文、必要章節缺漏。人工審查極容易漏，因為注意力會被語意問題吸走；而編號在多輪修訂後幾乎必然漂移（插入一條就讓其後所有引用失效）。這類交給集合比對，一秒解決。

**語意問題**——需求彼此矛盾、設計無法落地、遺漏既有流程的交界處。這類**只有不共享作者假設的人才看得見**。作者自己重讀一遍幾乎抓不到任何東西：他會沿著原本的思路再走一次，而錯誤正是藏在那條思路沒照到的地方。

實務觀察：一份經過三輪外部審查的 spec，每輪都找出實質問題，而作者自審只抓到機械性問題，**語意錯誤一個都沒抓到**。這不是能力問題，是視角問題。

## Step 0：載入

- `.shan/config.md`——缺就告訴使用者跑 `/shan-skills:shan-setup`；首行不是 `<!-- shan-config: v2 -->` 就提示一次「config 是舊版」，以現有內容繼續
- 草稿區檔案格式依 `${CLAUDE_SKILL_DIR}/../../docs/scratch-contract.md`（下稱**草稿區契約**）
- **判定模式**（見下一節）
- spec 在草稿區的 `spec-draft/` 還是已在正式 spec 目錄？**正式目錄受 hook 保護、不可寫**——修訂時見「修訂怎麼落」

## 模式：先判定是哪一道交接

| 條件 | 模式 | 守哪一道 |
|---|---|---|
| 審的是 `requirements.md`（`spec-draft/` 只有它，或使用者指定） | **需求模式** | SA → PG：requirements 能不能交出去 |
| 審的是 `doc-draft/` 的 `<名稱>_SD.md`（config A 節「系統設計書」為「有」） | **設計書模式** | SA → PG：SD 是否忠於 requirements、不與現況衝突 |
| `spec-draft/` 有 design／tasks | **完整模式** | PG → 開發：整份 spec 是否自洽、且忠於 requirements 與 SD |

判定不明確就問使用者，不要猜。模式寫進 `qa-report.md` 該輪標題。

**需求模式與設計書模式不跑下面的閘門 2、3、4 原文**，分別改跑「需求模式的閘門」與「設計書模式的閘門」；閘門 1 的格式比對照跑（只比 requirements 的部分，加上 `## Release Info`）。以下各閘門描述的是完整模式。

## 分級：不是每份 spec 都值得重炮

風險條件：

- **①** 動到熱路徑或共用基礎設施（認證、交易語意、稽核、核心查詢路徑）
- **②** 含不可逆的資料變更（schema migration、資料搬遷）
- **③** 跨模組，或改動既有流程的行為

| 符合幾項 | 建議做法 |
|---|---|
| 0–1 項 | 只跑閘門 1–3，約幾分鐘 |
| 2 項以上 | 加上閘門 4，至少一輪 |
| 3 項全中且需求數 > 10 | 閘門 4 跑到「連續一輪沒有阻斷級發現」為止 |

表中的「閘門 4」在需求模式即 R4，分級標準相同（風險條件以 requirements 描述的功能判斷）。

**開始前先跟使用者講清楚成本。** 一份動到熱路徑的 16 需求 spec 值得三輪；一份 3 需求的介面調整不值得。

## 閘門 1：格式

讀 config **A 節**指向的格式契約，逐項對照 spec 的標題與必要章節。

**先讀契約，再對照 2–3 份既有 spec 實證。這一步不能省。** 契約文件之間可能互相矛盾——實際踩過的案例：一份規範說「生成日期必須在第一行、標題之前」，另一份的檢查清單說「第一行必須是頂層標題」。**衝突時以既有 spec 的實際寫法為準**，因為那是工具真正接受的形式。

契約若提到 linter 或以字面比對標題，那些標題**一個字都不能改**（包括不能翻譯）。

---

## 閘門 2：識別字存在性

**這道閘門存在的理由**：spec 同時做兩件事——引用既有程式碼、命名尚未存在的新元件。這兩種模式的接縫是 hallucination 最容易發生的地方：作者以為自己在引用，實際上在發明。設計文件尤其危險，因為它本來就要大量命名新東西，「這個名字是我剛編的還是既有的」在寫作當下很難自我察覺。

作法：抽出文件中所有 backtick 包起來、看起來像型別 / 方法 / 欄位 / 設定鍵的識別字，逐一依 config **C 節**的查核路徑實際查證，分三類：

| 類別 | 處置 |
|---|---|
| 自稱既有、確實存在 | 通過 |
| 明說是新元件、找不到 | 正常，通過 |
| **自稱既有、卻找不到** | **立刻處理——那正是 hallucination 的形狀** |

處理時最重要的一點：**捏造的名稱往往連帶捏造了行為假設。** 真實的同類元件可能語意相反，那會讓建立其上的整段設計失效。

> 實際踩過的形狀：一份設計寫「重用既有的 MIME 偵測」，而真實存在的那支方法**失敗時會回退成某個圖片型別**——照該設計實作會讓 HTML 被判成圖片而 inline 顯示，直接違反兩條安全需求。改名字是五分鐘的事，**回頭確認設計是否還成立才是重點**。

本閘門只驗證**名稱存在**，不驗證**語意正確**。方法確實存在、但其失敗行為與文件敘述相反，這裡抓不到——那需要讀原始碼，屬閘門 4。

## 閘門 3：機械驗證

**用集合比對，不要用眼睛看。** 從閘門 1 讀到的契約推出各項語法，組出實際指令跑，再做集合運算：

| 檢查 | 作法 |
|---|---|
| 編號連續性 | 抽出所有需求／任務編號 → 檢查有無斷號 |
| 交叉引用完整性 | 抽出任務的回指編號集合 A、需求的實際編號集合 B → `A - B` 必須為空（引用了不存在的條文） |
| 需求涵蓋率 | `B - A` 就是未被任何任務涵蓋的需求（B 不含標「已移除」的墓碑） |
| 死術語 | 詞彙表定義了但全文再沒出現的詞 |
| 必要章節 | 契約的必要標題 − 文件實際標題 |

**每次修訂後都要重跑**，尤其是插入條文之後。

**編號一旦寫定就不得重排。** commit footer（config **G 節**）與任務的回指都硬綁編號，重排會讓所有既有 commit 的追溯失效。要新增一律**往後接號**。

涵蓋率不必 100%。裁決理由、明示的「不做」條款本來就沒有可執行行為——但它們必須在任務文件的備註章節**逐條列名交代**，而不是默默不見。把 `B - A` 的清單印出來逐條核對。

---

## 閘門 3b：交接檢查（完整模式）

requirements 是 SA 的契約，PG 端的 spec 必須**忠於它**。逐項實際比對，不憑印象：

| 檢查 | 作法 | 失敗的意思 |
|---|---|---|
| 已簽出 | `requirements.md` 的 `Status` 為 `released` | 需求還沒簽出就在做設計 |
| 未被動過 | 若有 `handoff-in/requirements.md`（與 SD 的 md），分別與 `spec-draft/` 裡的副本做 `diff`，必須為空 | PG 改了 SA 的需求或設計書。這是**阻斷級**——改回去，要改走 `req-questions.md` |
| rev 一致 | design（或 tasks）`**Based on:**` 記的 requirements rev（與 SD rev）等於兩者目前的 `Rev`；SD 的 `Based on` 也等於 requirements 目前的 `Rev` | 設計落後於需求或 SD。列出落差 rev 的 `Change Log` 每一則，逐項確認 design 決策與任務是否已跟上 |
| SD 已簽出 | 有 SD 時，其 `Status` 為 `released` | 在未簽出的設計書上做設計。只有 docx 的降級情形：報告註明「無法比對 rev」，其餘照跑 |
| SD 不被重寫 | design 對 SD 已定事項（資料表、DDL、URL、流程）是引用而非另寫一套；沒有與 SD 矛盾的陳述 | design 悄悄推翻或複製了 SD。矛盾以 SD 為準，該退回就走 `req-questions.md` |
| SD 項目有任務 | 列出 SD 的每項 DB 變更、URL 規格、檔案異動，逐項確認 tasks 至少有一個任務涵蓋 | SD 規定要做的事沒人排進任務 |
| 墓碑不被引用 | 標「已移除」的需求，沒有任何任務回指它 | 在做已被撤掉的需求 |
| 設計決策有出處 | design 每個決策都有 `serves Req X.Y`，且該編號存在、未移除 | 決策在服務不存在的需求 |
| 疑義已交代 | `req-questions.md` 沒有 `阻斷＝是` 且 `open` 的項目；`阻斷＝否` 的在 design 有「待確認」標記 | 設計建在未解的疑義上 |

沒有 `handoff-in/`（單人流程）時：「未被動過」改成確認 `Status` 與 `Rev` 合理即可；「已簽出」「SD 已簽出」只**提醒**（requirements 仍是 `draft`、或單人沒有 SD），**不判失敗**；沒有 SD 時「SD 不被重寫」「SD 項目有任務」不適用。這些都在 `qa-report.md` 註明為「單人流程」。簽出與版次比對是交接機制，沒有交接就不是缺陷。

## 閘門 4：對抗式語意審查

前三道機械可驗；這一道才是真正抓到問題的地方，也是唯一需要判斷力的。

**必須由不共享撰寫脈絡的獨立審查者執行。這是本 skill 最重要的一條。** 作法：用 Agent 工具 spawn 一個 subagent，**明確帶 `run_in_background: false`**，prompt 裡**只**放下列東西：

- spec 文件的路徑（只給成品，**不給** `grill.md`、不給撰寫過程的討論、不給設計理由）
- codebase 根目錄與 config **C 節**的查核路徑
- 下面「審查者要找什麼」的三類問題
- 回報格式：每則發現附 spec 原文引用、失敗情境、分級（阻斷級 / 文字層）

> ⚠️ **`run_in_background: false` 是硬性的。** Agent 工具預設背景執行；派完一個背景 subagent 之後你就沒有待辦了，這一輪會**當場結束**，閘門 4 的結果稍後落回**撰寫者**的 context——那正是本閘門存在的理由所要防的事。`shan-code-review` 曾因同一個根因失效過至少七次。**派出去之後要等它回來，自己讀完再往下走。**

**「我自己再讀一遍」不算數。** 已經驗證過：作者自審只抓得到機械性問題。使用者若偏好另開全新視窗跑，也算數。

**subagent 沒回來或失敗時**：在 `qa-report.md` 把閘門 4 標成「未執行：<原因>」，**MUST NOT 自己補審充數**，也不要因此宣告 spec 通過品保。

### 審查者要找什麼

依 spec 內容決定切分面向——不要照抄固定清單，那會退化成填表。但有三類問題**每次都值得專門看**，因為它們反覆出現（完整模式再加第四類，見最後）：

**① 新舊路徑的交界處（最高產的一類）。** spec 通常只描述新流程，而系統裡往往還有第二、第三條既有路徑在做同一件事。

> 形狀：spec 定義了「刪除資料要寫稽核」，卻漏掉「連鎖刪除父物件」那條路徑——它直接操作資料層繞過服務層，spec 宣稱的不變量在該路徑上完全不成立。

找法：**對 spec 涉及的每個核心動作，grep 整個程式碼庫看有幾個入口**，而不是只看 spec 提到的那個。

**② 前一輪修訂帶進來的新問題。** 每一輪審查的發現，多半源自上一輪的修法。

> 形狀：為了解決「執行緒暴量」改成分批交易，卻撞上前一輪剛確立的「稽核必須在 commit 前送出」——分批回滾會留下假稽核。

所以**最後一輪修訂過的部分，是下一輪最該看的地方**。

**③ 需求刻意的行為分歧被設計抹平。** 設計傾向追求「單一事實來源」，但需求有時刻意讓不同入口行為不同。

> 形狀：批次操作遇到鎖定中的項目要拒絕（防誤選），連鎖操作卻要放行（全量意圖明確）——一個不帶政策參數的共用函式無法表達這種分歧，照做會讓其中一條需求靜默落空。

**④ 設計或任務悄悄改寫了需求（完整模式）。** requirements 是 SA 的原意；PG 端的 design 與 tasks 可能在不自覺中縮小、放大或換掉它。

> 形狀：需求寫「所有角色」，設計的權限模型只留兩種角色；需求要求「保留已刪除項目 30 天」，任務只實作軟刪除而沒有清理期限的語意。

找法：審查者**同時拿 requirements、SD（若有）與 design／tasks**，逐條驗收條件問「照這份設計與任務做出來，這一條成立嗎？」；也問「SD 規定的流程與 DDL，tasks 有照做嗎？」。發現屬於 **requirements 或 SD 本身的問題**（含糊、矛盾）時，**不要由 PG 修**——寫進 `req-questions.md`。

### 收到審查報告後

**逐條查證再接受，不要照單全收。** 審查者也會判斷錯誤或有框架偏差。

> 形狀：一份審查正確指出「缺少某條分流」，但它推論的後果是「操作會失敗」，實際查證後是「會靜默刪除」——結論相同但理由相反，而寫進文件的必須是正確的那個失效路徑。

修訂時：

- 依契約的修訂標記格式記錄（含改到哪幾條），**累加不覆蓋**
- 新增條文**往後接號**，不插號不重編
- 改完**重跑閘門 2、3**——修訂本身會製造新的引用漂移
- 若修訂改變了設計決策，同步更新契約指定的決策章節，並在條文內寫出**裁決理由與接受之取捨**，讓下一位讀者不需重新推導

### 修訂怎麼落

- spec 在 `<草稿區>/<slug>/spec-draft/` → 直接改
- spec 已在正式目錄 → **hook 會拒絕寫入**，不要嘗試。把正式版複製到 `<草稿區>/<slug>/spec-draft/`，在複本上修訂，交付時告訴使用者「修訂後的版本在草稿區，請核可後自行搬回」

## 需求模式的閘門

守 SA → PG 這道交接。標準只有一個：**一個沒看過這場審訊的 PG，能不能只靠這份 requirements 設計並寫測試。**

### R1：格式

同閘門 1，只比 requirements 的標題與必要章節；另加 `## Release Info` 必須存在且欄位齊全（`Status` 此時應為 `draft`，`Rev`、`Change Log` 有當前 rev 的條目）。專案契約沒有 `Release Info` 時，它是團隊流程加的，不算違規。

### R2：技術字眼

requirements 不該有技術實作。抽出 backtick 包起來的識別字、檔案路徑、API 路徑、資料表／欄位名、程式碼片段、「快取」「queue」之類的做法詞——**每一個都是越界訊號**。客戶明確指定的技術限制可以留，但必須寫成限制並註明來源。這裡不查 codebase（SA 端通常沒有），只判斷該不該出現。

### R3：機械

同閘門 3 的集合比對，對象只有 requirements：

| 檢查 | 作法 |
|---|---|
| 編號連續 | 需求與驗收條件編號無斷號；**墓碑（已移除）算存在** |
| 編號不重用 | 與上一版（若有）比對：既有編號的標題語意沒被偷換成別的需求 |
| 句式 | 每條驗收條件符合契約的 EARS 句式，且一條一個 SHALL |
| 含糊詞 | 全文搜「適當」「盡快」「必要時」「合理」「儘量」「同現行」等，逐個確認有具體定義 |
| 死術語 | Glossary 定義了但全文再沒出現的詞 |
| Change Log | 與上一版逐項核對：Change Log 列的和實際動到的完全一致（沒列的沒動、列的都動了） |

### R4：對抗式語意審查

與閘門 4 同一條鐵則：**必須由不共享撰寫脈絡的獨立審查者執行，`run_in_background: false`，prompt 只放成品**——requirements 路徑、SA 專案目錄裡該主題的文件路徑（config **C 節**）、下面的問題類型、回報格式。**不給** `grill.md`。subagent 沒回來就標「未執行：<原因>」，不自己補審充數。

審查者要找：

- **① 與 SA 文件矛盾或遺漏**：requirements 與需求規格書、需求分析書、客戶問題單對不上；文件有的規則 requirements 沒有
- **② 不可測**：驗收條件沒有可觀察的結果、缺數字或條件
- **③ 少分支**：權限差異、錯誤路徑、邊界值、狀態轉換、與既有功能的交界漏掉了
- **④ 跨條矛盾**：兩條需求在某個輸入下要求相反的事
- **⑤ PG 會問什麼**：站在 PG 的位置讀一遍，列出他設計時一定會卡住、得回頭問 SA 的地方

### 需求模式的產出

- `qa-report.md` 該輪標題寫「模式：需求」，閘門列 R1–R4
- 修訂直接改 `spec-draft/requirements.md`；改動走 `shan-to-req` 的規則：**編號不重排**、有 `Rev` 的版本異動要同步 `Change Log`
- 需要 SA 拍板的取捨 → 開 `issues/` 票（`ready-for-human`）
- **通過後告訴使用者**：由 SA 手動把 `Status` 改 `released` 並填日期，再搬進 spec 目錄、交給 PG。**本 skill 不代簽出**

## 設計書模式的閘門

守 SA → PG 這道交接的另一半：系統設計書（SD）。標準：**PG 照這份 SD 做，行為會符合 requirements，而且不會撞到 codebase 現況。**

### D1：格式

同閘門 1，對照 config A 節「系統設計書」的格式契約。另驗 `## Release Info` 欄位齊全（`Status` 此時應為 `draft`，有 `Rev`、`Based on`、當前 rev 的 `Change Log`），以及契約固定項：每個功能段落有 `對應需求` 行。

### D2：現況查證

同閘門 2，對象是 SD 提到的每個資料表、欄位、型別、既有 URL、既有 service。依 config **C 節 / A 節「codebase 參考路徑」**實際查證，分類同閘門 2。額外兩項：

- SD 的 `ALTER`／新增是否與現況衝突（欄位已存在、型別不一致、命名撞到）
- DDL 的前置條件是否成立（例如改型別前假設的資料狀態）

**沒有 codebase 參考路徑時，這道標「未驗：無可查證的 codebase」**，不要用猜的通過。

### D3：機械

| 檢查 | 作法 |
|---|---|
| 需求涵蓋 | 抽出 requirements 的 Req 編號集合 B（排除「已移除」墓碑），SD 所有 `對應需求` 行的編號集合 A；`B − A` 逐條必須在 SD 明寫「不涉及設計變更」，否則是漏接 |
| 引用有效 | `A − B` 必須為空（SD 引用了不存在或已移除的需求） |
| requirements 已簽出 | requirements 的 `Status` 為 `released` | 在未簽出的需求上寫 SD。**提醒、不判失敗**：SD 的 `Based on` 註明了 `（draft）` 就視為使用者已知情並接受 |
| rev 綁定 | SD 的 `Based on` 等於 requirements 目前的 `Rev`；落後則列出 requirements `Change Log` 的落差項，逐項確認 SD 是否跟上 |
| 表格完整 | 欄位對照表、URL 規格表的每列欄數與表頭一致，沒有空儲存格卻沒說明 |
| Change Log | 與上一版（若有）逐項核對，列的和實際動到的一致 |

### D4：對抗式語意審查

鐵則同閘門 4：**獨立審查者、`run_in_background: false`、prompt 只放成品**——SD 路徑、requirements 路徑、codebase 參考路徑與 config C 節查核路徑、下面的問題類型、回報格式。**不給** `grill.md`。沒回來就標「未執行：<原因>」，不自己補審。

審查者要找：

- **① 與現況衝突**：DDL、欄位、URL 與 codebase 現有結構對不上；遺漏必要的資料轉換或 migration 順序
- **② 多入口差異**：SD 描述了一個入口，系統實際還有第二、第三個（不同版本、批次／單筆、後台／API）做同一件事，差異沒列
- **③ 行為落空**：requirements 的某條驗收條件，照 SD 的流程與資料模型無法成立
- **④ 錯誤路徑與交易**：失敗時回復什麼、補償動作、部分成功的處置沒寫，或寫的順序會留下不一致狀態
- **⑤ PG 會問什麼**：站在 PG 的位置讀一遍，列出他實作時一定會卡住、得回頭問 SA 的地方

### 設計書模式的產出

- `qa-report.md` 該輪標題寫「模式：設計書」，閘門列 D1–D4
- **本模式不就地修改 `doc-draft/` 裡的 SD**（契約規定該目錄已存在就不覆蓋，且人工可能編輯過）。發現的問題寫進 `qa-report.md`，逐項附 SD 原文引用與建議修法；修訂交回 `shan-to-sd` 的修訂流程（它會另存新版、`Rev` +1、`Change Log` 追加、`Status` 回 `draft`）
- 修訂後重跑本模式，直到 D1–D4 沒有阻斷級發現
- 發現 **requirements 本身的問題**（含糊、矛盾、缺分支）：寫進 `req-questions.md`，不要在 SD 裡默默補
- 需要 SA 拍板的取捨 → 開 `issues/` 票（`ready-for-human`）
- **通過後告訴使用者**：由 SA 手動把 `Status` 改 `released`，搬進文件目錄並交給 PG。**本 skill 不代簽出**

## 產出

修訂後的 spec 文件本身就是主要產出。另外：

1. **`<草稿區>/<slug>/qa-report.md`**（格式見草稿區契約，每輪追加）：四道閘門各自的結果帶數字、實質發現與文字層發現分開、你不同意審查的地方及理由、仍未解決的開放決策
2. **需要使用者拍板的取捨** → 在 `<草稿區>/<slug>/issues/` 開票（格式見草稿區契約，狀態 `ready-for-human`），並在回覆裡列出。產品語意、安全定位、上線切割這類決定會被寫進決策章節並約束後續所有實作，**不要自己選了往下走**
3. **查證出來、spec 該吸收但這輪沒改進去的事實** → 追加到 `<草稿區>/<slug>/findings.md`

閘門 4 跑了多輪就在 `qa-report.md` 說明每輪發現的性質變化。**問題從結構性轉為文字層，就是可以停的訊號**；每輪都還在出阻斷級發現，代表還沒收斂。

## 邊界

- 本 skill 只管 **spec 文件的正確性**，不做領域決策。
- **MUST NOT 寫入正式 spec 目錄**（hook 強制）。修訂一律落草稿區，由使用者搬。
- **完整模式下 MUST NOT 修改 `requirements.md`**，它是 SA 的契約。發現需求本身的問題，追加 `req-questions.md`，不要自己改。
- **需求模式與設計書模式下 MUST NOT 把 `Status` 改成 `released`。**
- **MUST NOT 為了讓閘門通過而放寬檢查**。涵蓋率不足就列出來交代，不要靠改需求編號讓數字好看。
