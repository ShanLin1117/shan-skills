# 系統設計書格式契約（預設）

專案有「系統設計書」（常見名稱：系統程式規格書、SD）這個交付物，又沒有既成慣例時用這份。`shan-setup` 會把它複製進專案（預設 `docs/specs/SD-FORMAT.md`），之後就是**專案的資產**。專案**沒有**這個階段就不用建，並在 config A 節寫「系統設計書：無」。

預設章節來自常見的「系統程式規格書」Word 範本；團隊範本不同就改成你們的。`shan-to-sd`、`shan-spec-qa`、`shan-to-spec` 只讀契約，不依賴本檔的任何標題，**除了**下面標明「固定」的三項（交接機制要靠它們）。

## 這份文件是什麼

系統設計書描述功能**怎麼在系統上落地**：畫面異動、資料流、資料表與欄位對照、DB 變更、URL／流程規格。它是 SA 交給 PG 的**設計契約**：DB 與介面的決定在這裡定案，PG 的 `design.md` 在它之下補實作層決策，不重寫、不推翻它。

三份文件的權威順序：`requirements.md`（行為）> 系統設計書（DB／介面／流程契約）> `design.md`（SD 之下的實作決策）。衝突時 PG 不自行裁決，走 `req-questions.md`。

檔名：`<功能名稱>_SD.md`。

## 標題契約

md 標題層級對應 Word 樣式層級；編號由樣式自動產生，**標題文字不要自己加編號**。

```markdown
# 功能說明

## 功能概述
<依哪張反應單／需求、要達成什麼>

# 功能規格

## <功能名稱>
**對應需求**：Req 1.1, 1.2

### 畫面規格
<畫面異動；截圖由人工貼入，這裡寫 ![說明](待補) 或文字描述>

### 資料流說明

#### 主要資料表
<例：G.S03；檔案系統存放路徑等>

### 主要欄位說明
| 序號 | 欄位名稱 | 資料庫及欄位 | 說明 |
|---|---|---|---|

### 功能操作與邏輯
<操作步驟、檢核規則、錯誤處理、交易與補償；條件分支用清單，流程可用 pseudocode 程式碼區塊>

### DB 變更
<DDL 與資料轉換語法；沒有就整節省略>

### URL 規格
| 版本 | URL | HTTP | 主要參數 |
|---|---|---|---|

## Release Info
- **Status**: draft
- **Rev**: 1
- **Released**:
- **Based on**: requirements rev 1

### Change Log
- **rev 1** (YYYY-MM-DD)：初版
```

- **固定一：每個 `## <功能名稱>` 底下有一行 `**對應需求**：Req X.Y, …`**。`shan-spec-qa` 靠它做 SD 與 requirements 的涵蓋比對（每條需求至少被一個功能段落對應；確實不涉及 SD 變更的需求，在該行或 `## 功能概述` 明寫「不涉及設計變更」）。轉 docx 時對應檔用 `drop_line_patterns` 濾掉這行，客戶版不顯示
- **固定二：檔尾 `## Release Info`**，欄位與規則同 requirements（見草稿區契約），另有 `Based on`：本版 SD 是依據 requirements 哪一版寫的。轉 docx 時對應檔用 `skip_sections` 略過整節
- **固定三：`Rev` 與 requirements 的 `Rev` 各自獨立**。只改 SD（例如補一個欄位）不必讓 requirements 升版，PG 看 SD 的 Change Log 就知道動了什麼
- 畫面截圖不由 AI 產生；DB 變更、URL 規格若本功能沒有，整節省略，不要留空標題
