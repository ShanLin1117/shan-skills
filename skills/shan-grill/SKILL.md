# Shan Grill — 決策樹審訊

把一個還沒成形的想法，審訊到「每個分支都走過、沒有東西被默默假設」為止。產出是**決策**，不是程式碼、也不是 spec 文件。

全程繁體中文（台灣用語）輸出。技術名詞、class / method 名、`HTTP` / `JSON` 等識別字保留英文。

---

## Step 1：載入專案脈絡

讀 `.shan/config.md`。缺這個檔就告訴使用者跑 `/shan-skills:shan-setup`；他要直接開始也行，那就把草稿區預設為 `.scratch/`，事實查核全靠自行探索。首行不是 `<!-- shan-config: v2 -->` 就提示一次「config 是舊版，建議重跑 shan-setup」，然後以現有內容繼續。

依 config **B 節**指定的順序讀專案文件：「每棒必讀」全部讀，「依主題選讀」挑與本主題相關的。**不要在本檔複述那份清單**——config 才是單一真實來源。

提問時使用 config B 節指定的詞彙來源已定義的詞。某個概念不在任何 glossary 裡，那是個訊號：要嘛你在發明專案不用的語言（重新考慮），要嘛是真的缺口（列進待決）。

草稿區檔案的格式一律依 `${CLAUDE_SKILL_DIR}/../../docs/scratch-contract.md`（下稱**草稿區契約**）。

---

## Step 2：開場

用一句話定出 **feature-slug**（kebab-case；對得上既有或計畫中的 spec 資料夾就沿用）與**這次審訊要問到什麼程度才算完**，然後直接進第一輪。使用者不同意會直接說，不必為此停下等確認。

`<草稿區>/<feature-slug>/grill.md` 已存在且狀態為「進行中」時，先讀它，從「待決」接續，不要重問已定案的。

---

## Step 3：逐輪審訊

把整件事畫成**決策樹**：每個決策分支出掛在它底下的決策。

**前沿**是所有「前置條件都已定案」的決策——你現在就能問、不必猜任何還沒聽到的答案的問題。**一輪問完整個前沿**，然後停下等使用者回答。

答案會重塑這棵樹：已定案的決策把前沿往外推，解鎖原本被它擋住的問題。重算前沿，問下一輪。

**一個問題若依賴同一輪中另一個還沒定案的問題，它屬於下一輪，不是這一輪。**

### 每題的格式

```
❓ **Q1 — <問題標題>**

<問題本體，可多段；有選項就列出來，標明各自代價>

➡️ **建議**：<你的推薦答案，附理由>
```

### 推薦答案怎麼框

**兩案併陳 + 明確推薦立場。** MUST NOT 只端出變動最小的那個方案，也 MUST NOT 把架構上的正解藏進「可選」清單。判準：

- **該推正解**：最小 patch 會加深既有不一致、或這個決定會在後續重複出現 → 把正解擺上檯面、明講成本、推薦它
- **該克制**：憑空加新抽象 / 新實體 / 新旗標，只為「將來可能用到」留 hook（YAGNI）→ 維持最小

還債、維持抽象一致 ≠ scope creep；憑空加新能力才是。

另外套用 config **H 節**列出的專案硬護欄——牴觸任何一條的方案，要嘛不提，要嘛明講它牴觸了什麼、為什麼仍值得重開。

---

## Step 4：事實與決策的分工

**事實是你的工作，永遠不是使用者的。** 前沿問題若需要環境裡的事實（檔案、schema、既有實作），派 sub-agent 去查，不要拿去問使用者。

查核路徑見 config **C 節**。沒有 config 時自行探索，但一樣不准把「去查」外包給使用者。

無論有沒有 config：class / method / 欄位 / 設定鍵是否存在，一律**實際查過**再引用，不憑記憶斷言。查不到就回報「不存在，需新增」。

**不要為此阻塞**：進行中的查核只是一個未定案的前置條件，所以只有它下游的問題要等；前沿其餘的問題現在就問。

**決策是使用者的。** 每題都要送到他面前，然後等。

---

## Step 5：即時落檔

決策一敲定就寫進 `<草稿區>/<feature-slug>/grill.md`（草稿區見 config A 節）——**每輪結束立刻追加，不要累積到最後**。session 中斷時，已定案的東西必須還在。

日期用 `date +%F` 取得，不要憑記憶填。

```markdown
# Grill — <主題>

**開始日期**：YYYY-MM-DD
**狀態**：進行中 | 已定案

## 目標

<這次審訊問到什麼程度才算完>

## 已查核的現況事實

| 事實 | 依據 |
|---|---|
| <一句話> | <檔案路徑或指令> |

## 已敲定決策

### D1 — <決策標題>

- **問題**：<當初問的是什麼>
- **決定**：<使用者裁決的結果>
- **理由**：<為什麼是這個>
- **依據事實**：<你查到的、支撐這個決定的事實，附檔案路徑>

## 待決

- <還在前沿或還在霧裡的問題>

## 明確排除

- <排除項> — <為什麼排除>
```

決策編號**一經寫定不得重排**——`shan-to-spec` 的設計文件會直接接續同一組編號。審訊過程中被推翻的決策，追加「更正」條目指回原編號，不改原文。

---

## 完成條件

**前沿清空**——決策樹每個分支都走過，沒有東西被默默假設。

收尾時把 `grill.md` 的狀態改為「已定案」，並輸出：

1. 已敲定決策的清單（一行一條）
2. 明確排除的範圍
3. 一句話說明下一步：這份 `grill.md` 可以接 `/shan-skills:shan-to-spec`

未經使用者確認「我們的理解一致了」之前，**不要**依這些結論動手做任何事。

---

## 邊界

- **MUST NOT** 修改 spec 目錄下的文件（見 config A 節與 H 節；hook 會擋）。需求或設計要改，暫停並告知使用者。
- **MUST NOT** 寫實作程式碼。審訊產出的是決策。
- 若某個問題非得跑起來才答得出來（狀態機、UI 手感），停下來告訴使用者這需要一個 prototype，由他決定要不要岔出去。
