# Shan Implement — 實作一棒

把 spec 的一棒任務變成綠燈的程式碼。**只做被指派的那一棒**，做完停下來。

全程繁體中文（台灣用語）輸出。程式碼註解依 config **H 節**的規定。

---

## Step 1：載入

1. **`.shan/config.md`** —— 缺就告訴使用者跑 `/shan-setup`
2. **spec 全部文件**（位置見 config A 節）——**動手前全部讀完**，三個角色分工不同：
   - **需求** 告訴你做什麼、為什麼（也是測試斷言的真實來源，**驗收條件原文要保留，不要過早摘要**）
   - **設計** 告訴你怎麼套進架構（模組配置、職責、資料流向、已定案決策）
   - **任務** 告訴你順序（也是 commit 邊界的真實來源）
3. **session 地圖**（若 `shan-plan` 產過）—— 讀「共通背景」與本棒細節，確認範圍柵欄與護欄。**它不是 spec**；範圍衝突時以 spec 為準。
4. **config D / E / G / H 節** —— 指令、測試慣例、commit 節奏、硬護欄

spec 有缺件就**停下來問**，不要憑空猜測。

---

## Step 2：確認範圍

找出下一個未完成的任務，讀它的子項與回指標記——那些編號指回需求，定義了「完成」的標準。

**動手前先跟使用者確認正在實作哪一個任務。** 一個任務 = 一次聚焦改動 = 一個 commit。不要靜悄悄跳到下一個。

**Session 範圍柵欄**：使用者若指定「本次只做到 X」，做完就**主動停下來報告**，明說「本 session 已結束，請開新視窗繼續」。**MUST NOT 因為「下一個任務看起來很簡單」就自行繼續**——session 邊界的意義是重置 context，不是難度判斷。

---

## Step 3：確認 seam

**seam** = 你觀察行為的公開邊界；測試住在 seam 上，不伸進內部。

- **設計文件已經議定 seam**（`shan-to-spec` 會寫進測試策略）→ 照著用，不要重新協商
- **沒有議定**（非 spec 驅動的改動，或 spec 沒寫）→ **列出你打算測的 seam，跟使用者確認過才寫第一個測試**

**MUST NOT 在未確認的 seam 上寫測試。** 測不完所有東西，事先議定 seam 是讓測試力氣落在關鍵路徑與複雜邏輯上、而不是每一個邊界案例的方法。

一併對照 config **E 節**決定測試型態與該繼承哪個基底，並找出既有的 prior art 照著寫。

---

## Step 4：開分支

Step 1–3 都是唯讀活動，隨時可以乾淨中止。**要開始寫檔案了，才開分支。**

命名依 config **G 節**。太早開分支的話，使用者一暫停討論或發現 spec 要改，就會留下沒 commit 的孤兒分支。

**MUST NOT 直接在預設分支上實作**（除非 config G 節另有規定）。

---

## Step 5：紅綠迴圈

**在 Step 3 議定的 seam 上，一次一刀。**

### 迴圈的規則

- **先紅後綠。** 先寫會失敗的測試，再寫剛好讓它通過的程式碼。不要預先滿足未來的測試，不要加投機性功能。
- **一次一刀。** 一個 seam、一個測試、一份最小實作，然後重複。
- **重構不屬於這個迴圈。** 它屬於審查階段。紅綠迴圈裡只做「讓這一刀綠」的事。

### 好測試的樣子

透過公開介面驗證**行為**，不驗證實作細節。程式碼可以整個換掉，測試不該跟著壞。測試名稱讀起來像規格——依 config **E 節**的命名慣例，並帶上回指驗收條件的標記（若 config E 節有規定）。

### 三個反模式

- **綁實作**——mock 內部協作者、測私有方法、走側門斷言（例如直接查資料庫而不是用介面）。徵兆：重構時測試壞了，但行為根本沒變。
- **同義反覆**——期望值是用跟程式碼同樣的方式算出來的（`expect(add(a,b)).toBe(a+b)`、手工推導出來的快照、常數等於自己），它由構造上必然通過，永遠不可能跟程式碼意見不合。**期望值要來自獨立的真實來源**：已知good的字面值、手算範例、spec 的驗收條件。
- **橫向切片**——先寫完所有測試，再寫所有實作。**這是 AI 最容易犯的一個。** 成批寫出來的測試驗證的是*想像中*的行為：你測到的是東西的*形狀*而不是使用者可見的行為，測試對真實變更變得不敏感，而且在理解實作之前就把測試結構定死了。改用**垂直切片**：一個測試 → 一份實作 → 重複，每個測試都回應上一輪學到的東西。

### 節奏

**頻繁跑單一測試檔，完整套件只在最後跑一次。** 完整驗證的成本見 config **D 節**——那通常是分鐘級的，不是每改一行都能跑的東西。

---

## Step 6：依設計實作

留在設計文件定義的模組配置裡。**設計沒講到的結構決策，問使用者，不要自己發明**——設計漂移是 spec 與實作不一致最常見的來源。

### 怎麼框決策點

設計未規定、需要你提案時，**MUST NOT 預設端出「對系統變動最小」的方案**。至少兩案併陳——最小 patch 與**架構一致的正解**——並**主動推薦後者**、講清楚長期理由：

- **推正解**：最小 patch 會加深既有不一致，或這個決定會在後續重複出現 → 把成本講明，由使用者拍板
- **維持最小**：較大的改動只是憑空加新抽象／新實體／新旗標，為「將來可能用到」留 hook → YAGNI

還既有架構債、維持抽象一致 **≠** scope creep；憑空加新能力才是。**MUST NOT 把正解默默藏起來只報最小 patch。** 架構級的正解若超出 spec 範圍，仍須上升到 spec（見下），不在程式碼裡偷改。

### 護欄

config **H 節**的每一條在實作全程有效。**MUST NOT 重複造輪子**——config H 節點名的既有基礎設施，一律用既有的。

---

## Step 7：驗證閘門

宣告完成前，跑 config **D 節**的完整驗證。要求：零編譯錯誤、零測試失敗、改動的檔案上零新警告。

**外部服務不可用時，照 config E 節的規定處置。** config 若寫明「停下來問」，就**停下來**——**MUST NOT** 用「只跑單元測試」「先跳過整合測試」繞過。

---

## Step 8：收尾

1. **勾選**任務文件裡對應的項目
2. **commit 節奏依 config G 節。** config 說要等使用者明確指示，就**停下來提出 commit 訊息草稿並等他點頭**；config 沒有特別規定就一任務一 commit。訊息格式、footer、禁忌全依 config G 節。
3. **自動跑第一輪審查**（見下）
4. **報告本棒結束**，並說明下一棒是什麼。

### 自動審查

**MUST NOT 用你自己的 context 審剛寫完的 code**——它已經被實作過程污染，你會沿著同一條思路再走一次，然後替每個選擇找到理由。

改成：**commit 完成之後**，spawn 一個 subagent 跑第一輪審查。

1. **時機**：一定在 commit **之後**。審查者比對的是 commit 後的 diff；還沒 commit 就 spawn，它看到的範圍是錯的。config G 節若要求等使用者點頭才 commit，就等到 commit 真的做完。
2. **冷 context**：**MUST NOT 把本視窗的實作對話帶進 subagent 的 prompt**。只給它：`shan-code-review` 這支 skill、spec 位置、本棒範圍（session 地圖的 S{X} 段，若有）、diff 的定點、以及 `<草稿區>/<feature-slug>/review-S<X>.md`（若已存在）。
3. **要求它**：依 `shan-code-review` 的格式回報，**不要修改任何檔案、不要 commit**。
4. **原文完整轉述**給使用者，**MUST NOT 過濾或淡化**。你是被審的那一方，摘要權在使用者不在你。
5. **MUST NOT 自動改程式碼。** 把發現整理成「必須修正 / 建議 / 可忽略」三類、各附修正方案，等使用者指定要改哪幾條再動手。
6. 改完重跑驗證閘門，綠燈後做一個**獨立的 follow-up commit**（節奏一樣依 config G 節）。獨立 commit 是為了讓下一輪審查的範圍界定得清楚。
7. 把本輪結果寫進 `<草稿區>/<feature-slug>/review-S<X>.md`（累加不覆蓋）。

**需要第 2 輪時，告訴使用者另開乾淨視窗跑 `/shan-code-review`——MUST NOT 在這個視窗連續審。** 走到這一步，你已經是那些修正的作者了，再審一次就回到自己審自己。

**加強版審查**：最後一棒、高風險棒次，或這一輪出了 🔴 時，建議使用者在自動這輪之外，另開視窗再跑一次手動審查當最終把關。

---

## Session context 健康度

出現下列任一情況，代表這個 session 的 context 已經過長：

- 對「之前做了什麼決定」不確定，需要回頭翻對話記錄
- 分不清某個類別或方法是「這個 session 新加的」還是「本來就有的」
- 命名或風格開始與前面的 commit 不一致

遇到就在**當前任務結束後**主動說：「建議在此 commit，開新視窗繼續剩下的任務，以確保後續品質。」

---

## 應避免的反模式

- **一次塞多個任務。** 即使下一個看起來也很簡單。commit 一旦不再對應任務，spec 與程式碼的可追溯性就死了。
- **發明需求。** 程式碼若需要需求文件沒寫的行為，停下來請使用者先更新 spec。
- **跳過設計文件。** 它定義模組配置、類別名稱、依賴關係。靜悄悄偏離就是缺陷。
- **預設用最寬的測試切片。** 挑能證明該行為的最窄切片（config E 節）。
- **為了讓測試綠而放寬斷言**，或加空的 try/catch 把錯誤吞掉。

---

## Spec 本身有問題時

spec 並非絕對正確。實作中若發現設計與需求互相矛盾、驗收條件技術上不可行、或明顯會在 production 出包的遺漏邊界情境：

**停止寫程式，告知使用者，等他們更新 spec。** **MUST NOT 在程式碼裡偷偷補洞**——那會讓 spec 失去意義。

---

## 邊界

- **只做被指派的那一棒。** 範圍外的問題記下來回報，不要順手修。
- **MUST NOT 修改 spec 文件。**
- **MUST NOT 自己審查自己的實作**（見 Step 8）。
- 對外動作（push、開 issue、發 MR）依 config **I 節**——預設一律需要使用者明確同意。
