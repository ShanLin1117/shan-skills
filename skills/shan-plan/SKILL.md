# Shan Plan — 開發計畫

在開始實作之前，把任務清單切成合理的 **session 邊界**，讓每一棒短小、聚焦、可驗收。

**長 session 是品質最大的隱性殺手。** 任務越多、context 越長，模型越容易開始偏離架構規範、累積小妥協、讓壞模式擴散。這支 skill 的目標是在那發生之前，先把地圖畫好。

全程繁體中文（台灣用語）輸出。

> ⚠️ **一棒 = 一個全新對話視窗。** 在同一個視窗連續做多棒，等於沒有切 session——context 污染依然存在。

---

## Step 1：載入

1. **`.shan/config.md`** —— 缺就告訴使用者跑 `/shan-skills:shan-setup`；首行不是 `<!-- shan-config: v2 -->` 就提示一次「config 是舊版」，以現有內容繼續
2. **spec 全部文件** —— 位置見 config **A 節**。**三個角色都要讀完**：需求（風險評估的來源）、設計（分層的主要依據）、任務（切割的對象）。只看任務清單會切錯
3. **既有的依賴圖** —— spec 的依賴圖章節就是阻塞邊，不要自己重新推導一份
4. **草稿區的既有檔**（格式見 `${CLAUDE_SKILL_DIR}/../../docs/scratch-contract.md`，下稱**草稿區契約**）：
   - `qa-report.md` —— 未解決的開放決策會影響切法
   - `findings.md` —— 前置盤點與跨棒事實；某些棒次的風險標記來自這裡
   - `issues/` 中 `Status` 非 `resolved` 的票 —— 被票擋住的任務要標出來
   - `session-map.md` 已存在時，**先讀它的 `## 修訂記錄`**，這次是更新而不是重切；已完成的棒次原樣保留
5. **config D / E / F / H 節** —— 建置指令、測試慣例、切法、硬護欄

跳過已完成的任務，只對未完成的做計畫。

---

## Step 2：評估每個任務

四個維度，快速判斷：

**A. 落在哪一層。** 層級定義從 spec 的設計文件與 codebase 實際結構推得，**不要套用固定清單**。多數專案大致是：資料層（schema / 遷移 / 資料存取）→ 邏輯層（業務規則）→ 介面層（對外 API / UI）→ 組態與接線。跨層的任務要標記。

**B. 依賴。** 誰擋住它、它擋住誰、哪些彼此獨立可換順序。以 spec 的依賴圖為準；圖與任務順序不一致時，那是 spec 的問題（見 Step 4）。

**C. 複雜度。**

- **低**——單一物件的增刪改查、單一模板修改
- **中**——跨 2–3 個類別、含分支邏輯、含測試設計
- **高**——跨層異動、非同步協調、安全相關、資料結構變更與邏輯同時動

**D. 風險。** 下列情境需要獨立一棒，或至少明確標示警語：

- 不可逆變更（schema migration、資料搬遷）
- 非同步 / 併發 / 交易邊界
- 安全相關（認證授權、輸入驗證、機密處理）
- 動到共用基礎設施，或影響既有的稽核 / 不變量
- 落在 config **H 節**任何一條硬護欄的射程內

---

## Step 3：切 session 邊界

分組原則**依 config F 節的切法而不同**，但優先序都一樣：

### `horizontal`（同層聚焦）

1. **依賴鏈優先** —— B 依賴 A，則兩者同棒或 A 在前一棒，不可倒置
2. **同層聚焦** —— 一棒內的任務落在相同或相鄰層級
   - ✅ 遷移 + 資料模型 + 資料存取（資料層一次做完）
   - ✅ 業務邏輯 + 對應測試
   - ✅ 對外介面 + 傳輸物件 + 文件註記
   - ❌ 遷移 + UI（跳層太大）
3. **複雜度上限** —— 高複雜度任務單獨一棒
4. **風險隔離** —— 高風險任務不與其他任務混棒

### `vertical`（貫穿切片）

1. **依賴鏈優先**（同上）
2. **一棒 = 一個完整切片** —— 從資料到介面到測試，做完可獨立驗證或 demo
3. **前置重構先做** —— 「先讓改動變容易，再做那個容易的改動」。能讓後續切片變簡單的重構，排在最前面獨立一棒
4. **風險隔離**（同上）

### 共同的規模指引

| 一棒的任務數 | 說明 |
|---|---|
| 1 | 高風險或高複雜度時**必須**；完整切片時最理想 |
| 2–3 | 低／中複雜度且同層或同切片，**最常見的健康大小** |
| 4 | 只在全部低複雜度且強依賴時才考慮 |
| > 4 | **禁止**——context 會太長 |

### 標出可並行的棒次

依賴圖上**阻塞者全部完成**的棒次構成**前沿**，彼此可以換順序、也可以在不同視窗並行。線性依賴鏈就是由上而下一棒一棒走。把前沿標出來——使用者才知道哪些順序是硬的、哪些是可調的。

## Step 4：攤出計畫，並主動提出 spec 問題

先在畫面上呈現完整計畫（每棒：包含的任務、層級、預計異動範圍、複雜度、風險、檢查點），再列出跨 session 注意事項。

**「異動範圍」寫模組或區域，MUST NOT 列具體檔案路徑。** 檔案路徑與「新增／修改」標註是計畫裡最快過期的東西——從計畫寫定到真正開工之間，spec 可能修訂、前一棒可能改變結構。寫「資料存取層與其遷移」，不要寫 `<某路徑>/XxxRepository`（新增）。實作那一棒自己去查，比計畫時猜的準。

**分析過程中若發現 spec 本身的問題，一併提出——但不要自己修 spec：**

- **任務範圍過大**（單一任務同時跨三層）→ 建議拆，指出拆點
- **依賴矛盾**（任務順序暗示的依賴與設計文件不一致）→ 點出具體衝突
- **遺漏測試任務**（有驗收條件但沒有對應的測試任務）→ 提醒
- **不可逆變更與其他層混在同一任務** → 建議獨立

問題若屬結構性，建議使用者回 `/shan-skills:shan-spec-qa` 補正再回來排計畫。非結構性的小問題（編號筆誤、設定鍵命名不一致）寫進地圖的「已知的 spec 小問題」節，讓開工的人留意。**MUST NOT 為了讓計畫好切而修改 spec。**

---

## Step 5：等使用者確認

**問三個具體問題，MUST NOT 問「這樣 OK 嗎」。** 開放式問句拿回來的多半是「OK」；具體問句才逼得出真回饋：

> 1. **粒度對嗎？** 有哪一棒太粗（一個視窗做不完）或太細（開視窗的成本大於內容）？
> 2. **阻塞關係對嗎？** 每一棒是不是只依賴真正擋住它的棒次——有沒有我排成了序列、其實可以換順序的？
> 3. **有沒有該合併或再拆的？** 特別是我因為高風險而獨立出來的那幾棒。
>
> 確認後我會寫成 session 地圖，並給你每一棒的開場 prompt。

等確認再進 Step 6。要調整就先改計畫再回到本步驟。**不要自動開始實作。**

---

## Step 6：產出 session 地圖與開場 prompt

### 6-1：寫出 session 地圖

路徑：`<草稿區>/<feature-slug>/session-map.md`（草稿區見 config A 節）。

**放草稿區而不是 spec 目錄**——它是規劃輔助檔，不是 spec 內容，也不該被 spec 的修改禁令綁住。已存在就更新主體並在 `## 修訂記錄` 追加一行說明這次重排了什麼，不要盲目覆寫。**不要 commit**，由使用者決定是否納入版控。

固定三大區——讓每一棒讀這一個檔就自足：

```markdown
# Session Map — <feature-slug>

> 這是開發計畫，**不是 spec 內容**。spec 才是權威來源。
> 用途：每次新開 impl / review 視窗時當固定抬頭讀入。
> 產出日期：YYYY-MM-DD。切法依 config F 節。

## 一、共通背景（每棒共用）

### 這份 spec 的定位
<在整體 roadmap 的位置、會動到哪些既有流程、相容性要求>

### Session 切割地圖
<表格：S1..Sn → 範圍 / 對應任務編號 / 前沿或阻塞關係 / 備註。高風險、需要外部服務、被 issues/ 擋住的棒次要標出來>
<紀律：做完綠燈 + commit 再開下一棒>

### 跨 session 硬性護欄（全程適用）
<從 config H 節與本 spec 抽出「每一棒都適用」的護欄，逐條列出>

### 每棒開場固定動作
**流程步驟一律依 shan-implement skill；本檔與 skill 衝突時以 skill 為準。** 這裡只記專案專屬的事：
- 分支名；上一棒必須已 commit
- 必讀清單：config B 節「每棒必讀」、本檔共通背景 + 本棒細節 + 修訂記錄、`findings.md`、未 resolved 的票
- 自動審查的呼叫參數：`<feature-slug> S{X} <本棒起點 commit>`；修正的 commit 政策（照抄 config G 節）
- 第 2 輪：另開視窗 `/shan-skills:shan-code-review <feature-slug> S{X} <修正 commit>`

### 建置與驗證指令
<照抄 config D 節>

### 已知的 spec 小問題
<開工時留意、但不需回 spec-qa 的項目；沒有就寫「無」>

## 二、各 Session 細節（只看自己負責那一棒）

### S1 — <名稱>
- 任務編號 / 層級 / 要讀的設計章節 / 預計異動範圍 / 風險 / 關鍵陷阱 / 檢查點
### S2 — ...

## 修訂記錄

- YYYY-MM-DD · shan-plan 初版 · —
```

### 6-2：在畫面輸出開場 prompt

寫完檔案後，**直接在回覆中列出**下列兩段供使用者複製（`<feature-slug>` 換成實際名稱，`{X}` / `N` 保留佔位）。

> **① 實作（每一棒開一個全新視窗）**
> ```
> /shan-skills:shan-implement 先讀 <草稿區>/<feature-slug>/session-map.md 的「共通背景」「S{X}」細節與「修訂記錄」，再讀同目錄的 findings.md 與 issues/ 中未 resolved 的票，然後依該棒範圍（任務 N）實作。做完跑該棒檢查點，綠燈後勾選對應任務，commit 前先讓我確認。
> ```
> `shan-implement` 會在 commit 之後**自動呼叫 fork 的 `shan-code-review`**（乾淨 context、兩軸平行），原文轉述結果、等你指定要修哪幾條，並依草稿區契約寫 `review-S{X}.md`。這一段不用你另外交代。
>
> **② 第 2 輪審查或最終把關（另開全新視窗）**
> ```
> /shan-skills:shan-code-review <feature-slug> S{X} <上一輪的修正 commit>
> ```
> 它會自己讀 `review-S{X}.md` 判定是第幾輪、照「多輪審查」規則縮小範圍、只報 🔴。報告末尾的「呼叫端待辦」告訴那個視窗接下來要做什麼。
>
> 什麼時候需要 ②：**最後一棒、高風險棒次、或第一輪出了 🔴 而你想確認修正沒問題時。** 中間棒次通常自動那輪就夠。
>
> **MUST NOT 在實作視窗連續審第 2 輪**——走到那一步，那個視窗已經是修正的作者了。

## 紀律：審查者的 context 必須乾淨

**reviewer 不能看過實作過程。** 這跟 `shan-spec-qa` 閘門 4 是同一條原則：作者沿著原本的思路再走一次，抓不到那條思路沒照到的東西。

v2 把這件事做成機制：`shan-code-review` 宣告 `context: fork`，**不論從哪裡呼叫**，它都在一個看不到呼叫端對話的 subagent 裡執行，並自己平行 spawn 兩軸。所以：

- 自動輪（`shan-implement` 呼叫）與手動輪（使用者另開視窗呼叫）跑的是**同一套機制**，差別只在呼叫端是不是作者
- 自動輪的呼叫端是作者，它拿到報告後只能**原文轉述、等使用者裁決**；手動輪的呼叫端是乾淨視窗，可以直接依裁決修
- 第 2 輪一定要另開視窗，因為自動輪的呼叫端已經是修正的作者

**順序鎖死，一棒一棒來。** 前一棒沒 commit，後面依賴它的驗證會跑不起來。審查也**必須**在該棒 commit 之後——reviewer 比對的是 commit 後的 diff。

**session 地圖不取代 spec。** `shan-code-review` 的真正輸入是 spec 加 diff；地圖只是幫它快速定位該棒範圍與護欄。

---

## 邊界

- **只做規劃，不寫程式碼。** 實作交給 `shan-implement`。
- **MUST NOT 修改 spec 文件。** 發現 spec 問題就告知使用者，結構性的建議回 `shan-spec-qa`。唯一產出是草稿區的 session 地圖。
- **不做 commit。** 計畫與地圖是給使用者的工作地圖，由他決定要不要納入版控。
