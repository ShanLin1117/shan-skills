# Shan Code Review — 雙軸審查

審查 `HEAD` 與一個定點之間的異動，沿兩條軸：

- **規範軸** —— 這段程式符合專案的慣例與設計品味嗎？
- **意圖軸** —— 它忠實做到了 spec（或這次改動想達成的事）嗎？

兩軸以**平行 subagent** 執行，彼此 context 不互相污染，最後並排回報。

全程繁體中文（台灣用語）輸出。

> ⚠️ **這支 skill 必須在乾淨的 context 執行。** 不要在剛寫完那段程式的同一個視窗呼叫——帶著實作記憶去審，等同自己審自己，會不自覺替實作合理化。另開新視窗，或由主 session spawn 一個冷 context 的 subagent。

---

## Step 0：這是第幾輪？

先看草稿區有沒有本棒的 `review-S<X>.md`。**有，就代表這是第 2 輪以後**——去讀「多輪審查」那一節，它會改變你的範圍與分級規則。沒有就是第 1 輪，照常往下走。

---

## Step 1：釘定範圍，並在這裡就失敗

**在 spawn 任何 subagent 之前**把範圍釘死。壞掉的 ref 或空 diff 要在這一步炸掉，**不要炸在兩個平行的 subagent 裡面**。

依序取得 diff：

```bash
git diff <定點>...HEAD      # 三點：與 merge-base 比較，排除定點分支自己的推進
git diff HEAD               # 尚未 commit 的工作目錄異動
```

- 使用者指定了 commit / branch / tag / PR 就用那個；沒指定就問，或取上游分支
- 先 `git rev-parse <定點>` 確認 ref 解得開，再確認 diff **非空**
- 同時記下 `git log <定點>..HEAD --oneline` 的 commit 清單
- 有未 commit 的異動、或範圍 diff 為空時，把工作目錄變更一起納入
- **未被改動的行**只在「同一個被改的函式內、改動重新暴露或未修好既有問題」時才納入

---

## Step 2：找出兩軸的依據來源

**意圖軸的依據**，依序找：

1. commit 訊息裡的 spec / 議題回指（依 config **G 節**的 footer 格式）
2. 使用者傳入的路徑
3. config **A 節** spec 目錄下與分支名或功能相符的 spec
4. `shan-plan` 產的 session 地圖（幫忙定位本棒範圍，**但它不是依據**——spec 才是）

都找不到就問使用者。他說「沒有 spec」，意圖軸就切到**無 spec 模式**（改判改動本身的正確性），並在報告裡註明。

**規範軸的依據**：config **B 節**列出的專案文件、config **E / G / H 節**，以及專案裡任何記載寫作規範的檔案。

---

## Step 3：平行 spawn 兩個 subagent

兩個一起發，不要串列。每個 prompt 都必須包含：

- 完整的 diff 指令與 commit 清單
- `.shan/config.md` 的路徑
- 該軸的檢查清單檔路徑（見下）
- **共同前置紀律**（原文帶進兩個 prompt）：

> **先形成預期，再看 diff。** 在打開任何程式碼或 diff 之前，先寫下：這次改動應該碰到哪些區域？關鍵行為對應的資料流、錯誤處理、回傳值、邊界條件應該長什麼樣？**形成獨立預期之後才去看實際實作**，兩相比對才是真正的審查。你沒參與實作，你的預期比實作者的選擇更接近意圖的原貌——不要被現有寫法錨定。
>
> **追蹤被刪掉的東西。** 對 diff 刪除或取代的每一行，先說出它原本守住的**不變量或行為**，再到新程式裡找那個不變量在哪重新建立。找不到就是候選問題（被移除的 guard、被吞掉的錯誤路徑、被放寬的驗證、被刪掉的測試）。
>
> **不要為了填欄位硬挑毛病。** 程式真的乾淨就回報「無」。寧可少報，也不要為了顯得認真而列無關緊要的觀察。

**規範軸 subagent** —— 加帶 [references/standards-axis.md](./references/standards-axis.md) 的路徑。

**意圖軸 subagent** —— 加帶 [references/intent-axis.md](./references/intent-axis.md) 的路徑，以及 spec 路徑（或「無 spec，走無 spec 模式」）。

兩者的回報都要求：**每則發現附檔案與位置、附具體失敗情境或引用的規範原文、標好分級（🔴 / 🟡 / 🟢）**。單軸報告控制在 600 字以內——字數上限是為了逼出優先序。

---

## Step 4：彙整，不要重排

把兩份報告放在 `## 規範軸` 與 `## 意圖軸` 兩個標題底下，原文或輕微整理後呈現。

**MUST NOT 合併或跨軸重新排名。** 兩軸是刻意分開的：

- 完全符合規範、但做錯了東西 → **規範軸過、意圖軸不過**
- 完全照 spec 做、但違反專案慣例 → **意圖軸過、規範軸不過**

分開報告，才不會讓一軸的通過遮蔽另一軸的失敗。結尾給一行摘要：**各軸各自的發現數與該軸內最嚴重的一項**。**不要跨軸挑一個總冠軍**——那正是分軸要防的重排。

---

## Step 5：處置

- **🔴 必修**（安全漏洞、無法編譯、破壞既有抽象、意圖軸的 spec 違反）→ **直接修**。動手前說一句「發現 X，正在修正」，修完確認沒引入新問題。
- **🟡 建議** → **不要自己改**，列給使用者決定。但 🟡 要再分兩類，**呈現方式不同**：
  - **架構債型** → 仍不動手，但 **MUST 明確表態推薦架構正解**，並講清楚「現在不修，債會怎麼複利」。不要中性羅列、不要跟裝飾性建議混在一起。
  - **裝飾性**（命名、抽共用、magic number）→ 中性列出即可。
- **🟢 觀察**（風格偏好）→ 只列出供參考，不動手。

下列情況**必須先問使用者**：需要新增 spec 沒列的功能或欄位、要動已 commit 且不在本次範圍的邏輯、發現 spec 本身有歧義或矛盾。

**MUST NOT 把 🟡 強行升級成 🔴 來合理化自己想改的東西。** 但「不動手」不等於「不表態」。

---

## 多輪審查

第 1 輪的修正，**在此之前沒有任何人審過**——那是新產生的程式碼。所以修正之後值得再審一輪。但多輪有個真實的失效模式，必須同時煞住。

### 失效模式：越審越肥

審查者有「找到東西」的壓力——回報「無發現」看起來像沒盡力，於是每一輪**降低門檻**：第一輪報結構性問題，第二輪報命名，第三輪報「這裡可以抽個 helper」。而 🟡 建議天然偏向「增加」（抽 helper、加抽象、加旗標、加防禦），很少有審查建議「這段刪掉」。累積三輪，就是三層沒人要求的抽象。

### 第 2 輪起的規則

1. **範圍縮小。** 審查對象是**修正 commit 的 diff** 加上記錄檔裡標為「已修正」的項目——**不是整棒重掃**。重掃必然又挖出新的 🟡。
2. **只報 🔴。** 🟡 / 🟢 **停止產出**。裝飾性建議在第 1 輪就該講完了；第 2 輪還在報命名，那是門檻滑落，不是盡責。
3. **已裁決不修的不要再報。** 記錄檔的「已裁決不修」是使用者拍過板的，重報等於推翻他的決定。
4. **主動檢查上一輪的修正有沒有引入過度工程。** 用規範軸第 8 條的「過度工程」那半邊掃自己造成的膨脹——為了修一個 🔴 而加的抽象、旗標、防禦，往往比原本的問題更貴。

### 收斂與硬上限

**停的條件**：🔴 歸零，**且**這一輪沒有新的結構性發現。

**硬上限三輪。** 第 3 輪還在出 🔴，**停止審查並上升**——那代表問題不在程式碼，在 spec 或設計。繼續審只會在錯的層級打轉。把還沒解決的 🔴 整理給使用者，建議回 `shan-spec-qa` 或重開設計討論。

### 記錄檔

每輪結束都要寫回 `<草稿區>/<feature-slug>/review-S<X>.md`，**累加不覆蓋**：

```markdown
## 第 N 輪 — YYYY-MM-DD — 範圍 <定點>...<HEAD>

### 已修正（修正 commit: <sha>）
- 🔴 <問題> → <怎麼修的>

### 已裁決不修（使用者決定）
- 🟡 <問題> — 理由：<使用者給的理由>

### 有異議
- <審查者的判斷與你查證後的結論不同之處>
```

日期用 `date +%F` 取得，不要憑記憶填。

---

## Step 6：跑測試

依 config **D 節**執行相關測試。測試紅燈就讀 log、找根因、修正、重跑，**不跳過不忽略**。外部服務不可用時照 config **E 節**處置，並在報告裡標明哪些驗證被擋住。

---

## Step 7：回報

```
## 審查結果：[通過 / 有問題已修正 / 待確認]

**範圍**：<定點>...HEAD（N 個 commit）　**意圖依據**：<spec 路徑 | 無 spec 模式>

### 意圖軸
<逐條驗收條件的狀態表；無 spec 模式改列「這次改動想達成什麼、有沒有達成」>

### 規範軸
> 沒發現就寫「無，程式整潔度良好」。

🔴 必修
- `path:line` — <問題> — <失敗情境>（已修正 / 需處理）

🟡 建議
［架構債型 — 附推薦立場］
- `path:line` — <問題>。**推薦改回正解**：<理由 + 不修的複利成本>
［裝飾性 — 中性列出］
- `path:line` — <觀察>

🟢 觀察
- <風格偏好>

### 修改項目
<只列實際動手改的；🟡 / 🟢 不列>

### 測試結果
### 結論
<各軸各自的發現數與該軸內最嚴重項；不要跨軸挑總冠軍>
```

**判定通過的條件**：意圖軸全數符合、規範軸無 🔴、測試全綠（或環境因素被擋住時明確標記）。🟡 / 🟢 不影響通過判定。

回報之後、使用者裁決完 🟡 之後，把這一輪寫進 `<草稿區>/<feature-slug>/review-S<X>.md`（格式見「多輪審查」）。**第 1 輪也要寫**——下一輪的乾淨視窗只能靠這個檔知道前面發生過什麼。

---

## 邊界

- **不 commit。** 只在使用者明確說 commit 之後才執行（config **G 節**）。
- **MUST NOT 修改 spec 文件。** 有問題告知使用者。
- **MUST NOT 自行實作未完成的任務。** 只審已完成的部分；發現缺漏就指出來。
- **MUST NOT 跳過測試失敗。**
- 對外動作依 config **I 節**。
