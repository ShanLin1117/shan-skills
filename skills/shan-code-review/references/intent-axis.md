# 意圖軸檢查清單

這段程式**忠實做到了它該做的事嗎**？依有沒有 spec 分兩種模式。

兩種模式都先做這件事：**對每個被改動的函式，用 Grep 找它的呼叫端與被呼叫端**，確認改動沒有破壞任一端的契約（回傳形狀變了、多了新例外、多了新前置條件、產生了時序依賴）。

---

## 模式 A：有 spec

### 逐條驗證

對這次範圍涉及的**每一條驗收條件**，逐一驗證實作。查證方式的優先序：

1. 讀原始碼確認邏輯與結構
2. 讀範本 / 介面定義確認對外形狀
3. 讀測試碼確認該條驗收條件真的被涵蓋
4. 對照設計文件的元件說明、資料流、錯誤處理

每條給出狀態：**符合 / 已修正 / 待確認 / 不符**，並附上你據以判定的位置。

### 三種要找的東西

- **(a) 缺漏或只做一半** —— spec 要求了，但 diff 裡沒有，或只做了一部分
- **(b) 沒人要求的行為（scope creep）** —— diff 裡有，但 spec 沒要求
- **(c) 看起來做了、但做錯了** —— 有對應實作，但行為與 spec 描述不符

**每則發現都要引用 spec 原文那一行。** 沒有引文的意圖軸發現，等於你在用自己的品味當標準——那是規範軸的事。

### 預期檔案 vs 實際檔案

從任務描述推出「應該被改動的區域」，跟 `git diff` 實際改的比對。**兩份清單的落差要列出來**——多出來的是候選 scope creep，少掉的是候選缺漏。

### 設計對齊

實作有沒有留在設計文件定義的模組配置裡？有沒有引入設計沒提過的新實體、新抽象？設計文件裡已定案的決策，實作有沒有默默違反？

## 模式 B：無 spec

沒有 spec，所以先從 diff 本身還原意圖：**這次改動想解決什麼問題、達成什麼行為？**（從 commit 訊息、函式名、被改的條件式推斷）把你還原出來的意圖**寫出來**——後面所有判定都以它為基準，也方便使用者糾正你理解錯了。

然後逐行問：**什麼輸入、狀態、時序或平台會讓這行錯？**

- 反向或錯誤的條件判斷、off-by-one、邊界值
- null / 空值解參考；falsy 的零或空字串被當成「沒有值」
- 競態、非同步與交易邊界、時序依賴
- catch 吞例外、錯誤被靜默、重試風暴
- 複製貼上後忘了改的變數、regex 沒跳脫的 metachar
- 改動後**呼叫端契約**是否仍成立

**每個疑慮都要能講出具體的失敗情境**（什麼輸入 / 什麼狀態 → 什麼錯誤結果）。講不出失敗情境的，不是意圖軸的發現。

**查證後能從程式碼直接否證的才剔除**——要引用實際的行、型別、常數或既有的 guard，不要靠「應該不會吧」。

## 兩種模式共同

### 追蹤被刪掉的東西

對 diff 刪除或取代的每一行，先指出它原本守住的**不變量或行為**，再到新程式裡找那個不變量在哪重新建立。找不到就是候選問題：

- 被移除的 guard 或驗證
- 被吞掉的錯誤路徑
- 被放寬的權限或範圍檢查
- 被刪掉、被 skip 的測試

### 測試是否真的證明了行為

測試存在不代表它有效。看：斷言的期望值是不是用跟實作同樣的方式算出來的（同義反覆，由構造上必然通過）？mock 有沒有蓋掉正要被驗證的那段邏輯？
