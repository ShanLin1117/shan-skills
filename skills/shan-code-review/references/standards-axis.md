# 規範軸檢查清單

這段程式**符合專案的慣例與設計品味嗎**？兩層：專案記載的規範（權威），加上一組通用的設計異味基線（判斷題）。

**專案規範覆蓋基線。** 專案明文背書的寫法，即使基線會標記它，也一律不報。
**跳過工具已經強制的東西**（formatter、linter、type checker 抓得到的，不要人工重報）。

---

## 第一層：專案規範（權威，違反可以是硬性問題）

依 `.shan/config.md` 的 **B 節**讀專案文件、**E / G / H 節**讀慣例，逐項對照。

### 1. 異動範圍
只改了該改的嗎？有沒有夾帶無關的格式化、import 重排、順手重構？跨檔修改是真的必要，還是該拆成獨立 commit？

### 2. 命名與可讀性
命名與既有 codebase 一致嗎（語言混用、縮寫、單複數）？magic number / magic string 該常數化或註明出處嗎？函式長度、巢狀深度、分支複雜度合理嗎？

### 3. 重複與重造輪子
有可抽共用的重複嗎？**既有的工具函式、helper、共用片段是不是被忽略而重寫了一份？** 特別對照 config **H 節**點名的既有基礎設施——那些是明文禁止重造的。

### 4. 錯誤處理
有沒有吞例外（空 catch、只記 log 不 rethrow）？用的是專案既有的例外體系，還是隨手拋通用例外？null / 空值處理一致嗎？

### 5. 安全
- **注入**：使用者輸入是否經過參數綁定 / 逃逸，而不是字串拼接
- **輸出逃逸**：寫進頁面或 DOM 的內容有沒有正確 escape
- **機密與個資**：log、錯誤訊息、回應裡有沒有落下密碼 / token / 金鑰 / 完整個資 / 完整 payload
- **請求偽造與授權**：狀態變更的端點有沒有該有的防護與權限檢查

### 6. 效能
迴圈內的查詢（N+1）？不必要的集合實體化？非同步 / 背景工作有沒有繼承該繼承的上下文？可能拉全表的查詢有沒有上限？

### 7. 框架與專案慣例
依 config **H 節**逐條對照。注入方式、交易邊界、抽象層的使用規則、對外回應的封裝、權限檢查——config 點名的每一條硬護欄都要看。

### 8. 過度工程 vs 架構漂移（**雙向**）

這條是雙向的，兩種相反的病都要抓：

**過度工程（往回收）**
- 引入超出 spec 範圍的新抽象、新實體、新設定旗標
- 未經測量就加快取 / 索引 / 非同步
- 為「將來可能用到」留 hook（YAGNI）

**架構漂移 / 局部最佳（往正解推）**
- 這次實作是不是挑了「對系統變動最小」的省事 patch，而**加深了既有不一致**？（該走既有抽象層卻就近綁具體實作；該用既有例外卻新拋通用例外；該用既有共用元件卻又複製一份）
- 這個寫法**會在後續重複出現**嗎？（同一模式被複製到第二處、第三處）如果會，現在的最小 patch 就是在累積債。

**判準**：還既有架構債、維持抽象一致 **≠** scope creep；憑空加新能力才是。發現「省事 patch 加深漂移」時列為**架構債型 🟡**，明確表態推薦正解並講清楚不修的複利成本，**不要中性帶過**。

### 9. 可觀測性（log 夠不夠）

> **為什麼有這條**：AI 預設用「最乾淨」的方式寫程式，常常完全不加 log。但維運要能從 log 還原「這段功能做了什麼、走到哪、為什麼失敗」。第 7 條看 log 的**寫法**，這條看 log **夠不夠**。

**判準（不是每步都要記）**：以「維運人員半夜只看 log，能否判讀這段功能是否正常、出錯時錯在哪」為尺度。不足要報，過度 noise 也要提醒。

- **成功路徑要有 INFO 里程碑**：業務進入點與結束、外部呼叫前後、重要分支結果、關鍵數量。**不要求**每個私有 helper 都記。
- **失敗與例外路徑要有 ERROR**，例外物件本身要被帶進去。**禁止**空 catch，或「catch 後既不記也不 rethrow」讓故障無聲。
- **降級 / 重試 / fallback / 逾時要有 WARN**，並說明為何降級。
- **迴圈內不要逐筆 INFO**：改 DEBUG，或迴圈後記一筆 summary。
- **不得記**密碼 / token / 金鑰 / 完整個資 / 完整 payload。

**分級**：吞例外導致故障無聲、外部呼叫失敗完全無 ERROR → **🔴**；缺 INFO 里程碑、成功路徑不可觀測 → **🟡**（列出建議補點，**不要自己塞一堆 log**）；過度 log → 🟡 / 🟢，提醒收斂。

### 10. 測試品質（不只看有沒有）
測試名稱描述的是**行為**還是方法？有沒有涵蓋正常路徑 + 錯誤路徑 + 邊界？有沒有誤用 mock 蓋掉真實邏輯導致測試失去意義？有沒有依 config **E 節**用既有的測試基底而不是自建一套？

## 第二層：設計異味基線（永遠是判斷題）

專案什麼都沒記載時，這一層仍然適用。每一條都是**帶標籤的啟發式**（「可能有 Feature Envy」），**永遠不是硬性違規**。格式是「它是什麼 → 怎麼修」：

- **神祕命名** —— 函式、變數或型別的名字沒有透露它做什麼、裝什麼。→ 改名；如果想不出誠實的名字，代表設計本身還混沌。
- **重複程式碼** —— 同一個邏輯形狀出現在不只一個 hunk 或檔案。→ 抽出共用形狀，兩邊都呼叫它。
- **依戀情結（Feature Envy）** —— 某個方法動別人的資料比動自己的還多。→ 把方法搬到它所依戀的資料上。
- **資料泥團** —— 同幾個欄位或參數老是一起旅行（一個想被生出來的型別）。→ 打包成一個型別，傳那個。
- **基本型別偏執** —— 用基本型別或字串代替一個值得擁有自己型別的領域概念。→ 給那個概念一個小型別。
- **重複的 switch** —— 對同一個型別的 `switch` / `if` 串在異動中反覆出現。→ 換成多型，或一張兩處共用的對照表。
- **散彈式修改** —— 一個邏輯上的改動逼你在 diff 裡改很多檔。→ 把一起變的東西收進同一個模組。
- **發散式變化** —— 同一個檔案或模組因為好幾個無關的理由被改。→ 拆開，讓每個模組只為一個理由變。
- **投機性通則** —— 為 spec 沒有的需求加的抽象、參數或 hook。→ 刪掉；inline 回去，等真的有需求再說。
- **訊息鏈** —— 長長的 `a.b().c().d()` 導航，呼叫端不該依賴這條路徑。→ 把整段走訪藏進第一個物件的一個方法後面。
- **中間人** —— 一個類別或函式大部分只是往下轉手。→ 砍掉，直接呼叫真正的目標。
- **被拒絕的遺贈** —— 子類別或實作者忽略、覆寫掉它繼承來的大部分東西。→ 拿掉繼承，改用組合。
