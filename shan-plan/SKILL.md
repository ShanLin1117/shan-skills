# Shan Plan — 開發計畫

在開始實作之前，把任務清單切成合理的 **session 邊界**，讓每一棒短小、聚焦、可驗收。

**長 session 是品質最大的隱性殺手。** 任務越多、context 越長，模型越容易開始偏離架構規範、累積小妥協、讓壞模式擴散。這支 skill 的目標是在那發生之前，先把地圖畫好。

全程繁體中文（台灣用語）輸出。

> ⚠️ **一棒 = 一個全新對話視窗。** 在同一個視窗連續做多棒，等於沒有切 session——context 污染依然存在。

---

## Step 1：載入

1. **`.shan/config.md`** —— 缺就告訴使用者跑 `/shan-setup`
2. **spec 全部文件** —— 位置見 config **A 節**。**三個角色都要讀完**：需求（風險評估的來源）、設計（分層的主要依據）、任務（切割的對象）。只看任務清單會切錯。
3. **既有的依賴圖** —— spec 的依賴圖章節就是阻塞邊，不要自己重新推導一份
4. **config D / E / F / H 節** —— 建置指令、測試慣例、切法、硬護欄

跳過已完成的任務，只對未完成的做計畫。

---

## Step 2：評估每個任務

四個維度，快速判斷：

**A. 落在哪一層。** 層級定義從 spec 的設計文件與 codebase 實際結構推得，**不要套用固定清單**。多數專案大致是：資料層（schema / 遷移 / 資料存取）→ 邏輯層（業務規則）→ 介面層（對外 API / UI）→ 組態與接線。跨層的任務要標記。

**B. 依賴。** 誰擋住它、它擋住誰、哪些彼此獨立可換順序。以 spec 的依賴圖為準；圖與任務順序不一致時，那是 spec 的問題（見 Step 4）。

**C. 複雜度。**

- **低**——單一物件的增刪改查、單一模板修改
- **中**——跨 2–3 個類別、含分支邏輯、含測試設計
- **高**——跨層異動、非同步協調、安全相關、資料結構變更與邏輯同時動

**D. 風險。** 下列情境需要獨立一棒，或至少明確標示警語：

- 不可逆變更（schema migration、資料搬遷）
- 非同步 / 併發 / 交易邊界
- 安全相關（認證授權、輸入驗證、機密處理）
- 動到共用基礎設施，或影響既有的稽核 / 不變量
- 落在 config **H 節**任何一條硬護欄的射程內

---

## Step 3：切 session 邊界

分組原則**依 config F 節的切法而不同**，但優先序都一樣：

### `horizontal`（同層聚焦）

1. **依賴鏈優先** —— B 依賴 A，則兩者同棒或 A 在前一棒，不可倒置
2. **同層聚焦** —— 一棒內的任務落在相同或相鄰層級
   - ✅ 遷移 + 資料模型 + 資料存取（資料層一次做完）
   - ✅ 業務邏輯 + 對應測試
   - ✅ 對外介面 + 傳輸物件 + 文件註記
   - ❌ 遷移 + UI（跳層太大）
3. **複雜度上限** —— 高複雜度任務單獨一棒
4. **風險隔離** —— 高風險任務不與其他任務混棒

### `vertical`（貫穿切片）

1. **依賴鏈優先**（同上）
2. **一棒 = 一個完整切片** —— 從資料到介面到測試，做完可獨立驗證或 demo
3. **前置重構先做** —— 「先讓改動變容易，再做那個容易的改動」。能讓後續切片變簡單的重構，排在最前面獨立一棒
4. **風險隔離**（同上）

### 共同的規模指引

| 一棒的任務數 | 說明 |
|---|---|
| 1 | 高風險或高複雜度時**必須**；完整切片時最理想 |
| 2–3 | 低／中複雜度且同層或同切片，**最常見的健康大小** |
| 4 | 只在全部低複雜度且強依賴時才考慮 |
| > 4 | **禁止**——context 會太長 |

### 標出可並行的棒次

依賴圖上**阻塞者全部完成**的棒次構成**前沿**，彼此可以換順序、也可以在不同視窗並行。線性依賴鏈就是由上而下一棒一棒走。把前沿標出來——使用者才知道哪些順序是硬的、哪些是可調的。

---

## Step 4：攤出計畫，並主動提出 spec 問題

先在畫面上呈現完整計畫（每棒：包含的任務、層級、預計異動範圍、複雜度、風險、檢查點），再列出跨 session 注意事項。

**分析過程中若發現 spec 本身的問題，一併提出——但不要自己修 spec：**

- **任務範圍過大**（單一任務同時跨三層）→ 建議拆，指出拆點
- **依賴矛盾**（任務順序暗示的依賴與設計文件不一致）→ 點出具體衝突
- **遺漏測試任務**（有驗收條件但沒有對應的測試任務）→ 提醒
- **不可逆變更與其他層混在同一任務** → 建議獨立

問題若屬結構性，建議使用者回 `/shan-spec-qa` 補正再回來排計畫。**MUST NOT 為了讓計畫好切而修改 spec。**

---

## Step 5：等使用者確認

> 這個切法 OK 嗎？有沒有要調整的 session 邊界或任務分組？確認後我會寫成 session 地圖，並給你每一棒的開場 prompt。

等確認再進 Step 6。要調整就先改計畫再回到本步驟。**不要自動開始實作。**

---

## Step 6：產出 session 地圖與開場 prompt

### 6-1：寫出 session 地圖

路徑：`<草稿區>/<feature-slug>/session-map.md`（草稿區見 config A 節）。

**放草稿區而不是 spec 目錄**——它是規劃輔助檔，不是 spec 內容，也不該被 spec 的修改禁令綁住。寫檔前先確認同名檔不存在；已存在就更新，不要盲目覆寫。**不要 commit**，由使用者決定是否納入版控。

固定兩大區——讓每一棒讀這一個檔就自足：

```markdown
# Session Map — <feature-slug>

> 這是開發計畫，**不是 spec 內容**。spec 才是權威來源。
> 用途：每次新開 impl / review 視窗時當固定抬頭讀入。

## 一、共通背景（每棒共用）

### 這份 spec 的定位
<在整體 roadmap 的位置、會動到哪些既有流程、相容性要求>

### Session 切割地圖
<表格：S1..Sn → 範圍 / 對應任務編號 / 前沿或阻塞關係 / 備註。高風險與需要外部服務的棒次要標出來>
<紀律：做完綠燈 + commit 再開下一棒>

### 跨 session 硬性護欄（全程適用）
<從 config H 節與本 spec 抽出「每一棒都適用」的護欄，逐條列出>

### 每棒開場固定動作
<確認上一棒已 commit → 從第一個未完成子任務開始 → 收尾勾選任務 + 跑檢查點 + 依 config G 節的節奏處理 commit>

### 建置與驗證指令
<照抄 config D 節>

## 二、各 Session 細節（只看自己負責那一棒）

### S1 — <名稱>
- 任務編號 / 層級 / 要讀的設計章節 / 預計異動範圍 / 風險 / 檢查點
### S2 — ...
```

### 6-2：在畫面輸出開場 prompt

寫完檔案後，**直接在回覆中列出**下列三段供使用者複製（`<feature-slug>` 換成實際名稱，`{X}` / `N` 保留佔位）。①② 是手動雙視窗，③ 是整合版——**擇一使用，不要同時跑**。

> **① 實作（每次開全新視窗）**
> ```
> /shan-implement 先讀 <草稿區>/<feature-slug>/session-map.md 的「共通背景」與「S{X}」細節，再依該棒範圍實作。做完跑該棒檢查點，綠燈後勾選對應任務，commit 前先讓我確認。
> ```
>
> **② 審查（實作 commit 後，另開全新視窗）**
> ```
> /shan-code-review 先讀 <草稿區>/<feature-slug>/session-map.md 的「共通背景」與「S{X}」細節，再審查 S{X}（任務 N）的實作。
> ```
>
> **③ 整合版（實作 + 自動冷 context 審查，同一個全新視窗）**
> ```
> /shan-implement 先讀 <草稿區>/<feature-slug>/session-map.md 的「共通背景」與「S{X}」細節，再依該棒範圍（任務 N）實作。做完跑該棒檢查點，綠燈後勾選對應任務，commit 前先讓我確認。
>
> 【實作完成後的自動審查流程】
> 等我確認並完成 S{X} 的 commit 之後：
> 1. spawn 一個 subagent，冷 context——不要把本視窗的實作對話帶過去。
> 2. 指示它呼叫 shan-code-review，內容為：「先讀 <草稿區>/<feature-slug>/session-map.md 的「共通背景」與「S{X}」細節，再審查 S{X}（任務 N）。審查基準是 spec 加上本次 commit 的 diff。依 shan-code-review 的格式回報，不要修改任何檔案、不要 commit。」
> 3. 把它的審查結論「原文完整轉述」給我，不要過濾或淡化。
> 4. 不要自動改程式碼。先把發現整理成「必須修正 / 建議 / 可忽略」三類並附修正方案，等我確認要改哪幾條再動手。
> 5. 修正完重跑檢查點，綠燈後做一個獨立的 follow-up commit（一樣先讓我確認）。
> ```

---

## 紀律：審查者的 context 必須乾淨

**reviewer 不能看過實作過程。** 這跟 `shan-spec-qa` 閘門 4 是同一條原則：作者沿著原本的思路再走一次，抓不到那條思路沒照到的東西。

- 手動模式靠「另開全新視窗」達成
- 整合版靠「spawn 冷 context 的 subagent」達成
- **同一視窗直接接著審剛寫的 code 不算**——context 已被污染

**整合版的權衡**：審查結論經由「身為作者的主 session」轉述，已要求原文完整轉述且修正前先由使用者拍板；要最高純度把關，仍可在整合版之外另開視窗再審一次。整合版適合快速回合，手動雙視窗適合最終把關。

**順序鎖死，一棒一棒來。** 前一棒沒 commit，後面依賴它的驗證會跑不起來。整合版的 subagent 也**必須**在該棒 commit 之後才 spawn——reviewer 比對的是 commit 後的 diff。

**session 地圖不取代 spec。** `shan-code-review` 的真正輸入是 spec 加 diff；地圖只是幫它快速定位該棒範圍與護欄。

---

## 邊界

- **只做規劃，不寫程式碼。** 實作交給 `shan-implement`。
- **MUST NOT 修改 spec 文件。** 發現 spec 問題就告知使用者。唯一產出是草稿區的 session 地圖。
- **不做 commit。** 計畫與地圖是給使用者的工作地圖，由他決定要不要納入版控。
